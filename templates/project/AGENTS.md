# {{APP_NAME}} AI開発ルール

このファイルは、人間とCodexエージェントがこのリポジトリで開発するときの共通ルールです。実装を始める前に、実際のリポジトリ構成、build、test、リリース手順を調査してこの文書へ追記してください。

## オーケストレーション

- AI駆動開発の設計: `docs/AI_DRIVEN_DEVELOPMENT.md`
- プロダクト仕様の入口: `docs/00_INDEX.md`
- 進行中の実行計画: `docs/exec-plans/active/`
- 完了済みの実行計画: `docs/exec-plans/completed/`
- プロジェクト固有subagent: `.codex/agents/`

メインエージェントをデフォルトの実行主体とします。要求整理、調査、実装、検証、統合、完了判定は、作業が十分小さい場合または必要なコンテキストを保持している場合、メインエージェント自身が実行します。

subagentは、委譲による利益がコンテキスト再読込、通信、待機、統合のコストを上回る場合にだけ使用します。利用できること自体を利用理由にしません。

### subagentを使用する条件

- 独立した2つ以上の作業を並列化できる。
- 専門的な調査や独立レビューをメイン作業から分離する価値がある。
- 対象範囲が明確で、限定されたファイルまたは情報だけで完結できる。
- 長時間のread-heavyな探索をメインエージェントのコンテキストから分離する必要がある。
- 高リスク変更で、実装者とは独立したQAまたはレビューが必要である。

次の場合は原則としてsubagentを使用しません。

- 1〜3ファイル程度の小規模変更。
- 単純な不具合修正、軽微なUI変更、短い文書変更。
- メインエージェントが必要な仕様とコードをすでに把握している作業。
- subagentが同じ仕様書やコードを再読込するだけになる作業。
- 先行作業へ依存し、並列化やコンテキスト分離の利益がない作業。

### 委譲ルール

- 必要なファイル、仕様、目的、制約だけを渡し、リポジトリ全体の再読込を求めません。
- 同じファイルを複数のwrite agentに同時割り当てません。
- 同時subagent数は原則2〜3までとし、依存作業を無理に並列化しません。
- 通常の機能実装はユーザーが開いている現在のcheckoutで行い、別worktreeや別ディレクトリを自動作成しません。
- 現在のcheckoutで既存変更と安全に両立できない場合は、別worktreeへ自動退避せずユーザーへ方針を確認します。
- 結果は結論、変更ファイル、検証結果、問題または未解決事項に絞ります。

### QA

小規模変更ではメインエージェント自身によるbuild、test、Simulator確認を許可します。独立QAは、データ消失、日付計算、通知、永続化、移行、課金、認証、複数画面変更、大規模リファクタリング、またはユーザーが明示的にレビューを求めた場合に使用します。QA担当は原則として不具合を直接修正しません。

## ドキュメントファースト

1. 新規プロダクトは`docs/01_PRODUCT_CONCEPT.md`から始め、対象ユーザー、課題、価値、非対象、差別化、成功指標を決定または明示的に仮決定します。
2. 実装開始前に、`docs/00_INDEX.md`から`docs/08_DECISIONS_AND_OPEN_QUESTIONS.md`までのうち対象に必要な文書を埋め、観測可能な受け入れ条件と検証計画を定義します。
3. 新機能や仕様変更では、影響する要件、UX、技術設計、データ、ロードマップ、テスト、決定事項をコード変更前に更新します。
4. 製品挙動、データ安全性、アーキテクチャ、課金、プライバシー、リリース範囲を変える未決定事項がある場合、ユーザーが仮決定を明示的に受け入れるまで実装を開始しません。
5. 仕様を変えない限定的な不具合修正、テストのみ、リファクタリング、機械的保守では既存文書を再利用できます。仕様との不一致を発見した場合は先に文書へ反映します。
6. 文書は規模に比例させ、同じ情報を持つ正本を重複して作りません。

## 変更と検証

1. 作業前に`git status --short --branch`を確認します。
2. 既存の未コミット変更をユーザーの作業として保護します。
3. `main`上では変更せず、リポジトリの規約に従う作業ブランチを作成します。
4. 要件を観測可能な受け入れ条件にしてから実装します。
5. 対象のbuild、自動テスト、Simulator操作、アクセシビリティ確認をリスクに応じて実行します。
6. 検証できなかった項目は理由と残存リスクを報告します。
7. 変更後に無関係なファイル、秘密情報、生成物が含まれていないことを確認します。
